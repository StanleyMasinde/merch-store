## Merch Store

Merch Store is a sample Rust web application demonstrating the usage of my [Daraja SDK](https://github.com/StanleyMasinde/daraja-sdk) (an experimental Rust client for Safaricom's M-Pesa API), Axum, and Toasty ORM.

## Running

1. Clone this repo.
2. Copy `config.toml.example` to `config.toml`
3. Update `config.toml` with your Daraja credentials.
4. Run the app with `cargo run` — it will start the server at `localhost:3000`
5. You can test it with this curl command
```shell
curl  "localhost:3000/pay" --json '{"phone_number": <phone number to prompt>, "amount": 1}'
```
That's it for now.

## Database migrations

Migrations are handled by a separate `cli` binary (built from `src/bin/cli.rs`), backed by Toasty's migration system. Migration config lives in `Toasty.toml`, with generated SQL, snapshots, and history tracked under `database/`.

### Generating a migration

After changing a model struct:

```shell
cargo run --bin cli -- migration generate
```

Review the generated SQL in `database/migrations/` before committing. Commit `database/migrations/`, `database/snapshots/`, and `database/history.toml` alongside the model change.

### Applying migrations

```shell
cargo run --bin cli -- migration apply
```

This reads `config.toml` from the current directory.

### Deploying (Suggestion)

In production, `merch_store` is built once in CI (no `cargo` on the server) and shipped via `rsync`. `config.toml` lives on the server at `/etc/merch-store/config.toml` and is never present in CI — it's provisioned once, out-of-band, and never rsynced or regenerated by the deploy pipeline. Pending migrations apply automatically when the server starts (see `start_server` in `src/server/app.rs`), so the `cli` binary and `database/` directory are only needed in dev for `migration generate`.

```
/etc/merch-store/
└── config.toml

/var/www/merch_store/
└── merch_store
```

Deploy flow:

1. Build in CI (`cargo build --release`)
2. `rsync` `merch_store` to the server
3. Restart the systemd service (`sudo systemctl restart merch_store`), with the unit passing the config path positionally, e.g. `ExecStart=/var/www/merch_store/merch_store /etc/merch-store/config.toml`
4. Check logs after restart (`journalctl -u merch_store`): a failed migration is logged and does not block startup, so verify `applied N migrations` before considering the deploy done
